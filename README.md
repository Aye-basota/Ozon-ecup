# Ozon e-cup — Ценность пользователей поиска

## О проекте

По дневной истории активности пользователя в Поиске и Каталоге
(запросы, корзины, покупки) предсказываем суммарный GMV за следующие 30 дней.
Горизонт теста: **2026-02-14 .. 2026-03-15**, 250 000 пользователей.

## Метрика

**RMSLE** с `log1p`, отрицательные предсказания клипятся нулём.
Это обычный MSE в переменной `z = log1p(y)` — значит, L2-регрессия на `log1p(y)`
оптимизирует метрику точно, кастомный лосс не нужен.

## Валидация (единая для всех)

Out-of-time cutoff-схема, `src/validation.py`:

- на каждом cutoff `T` признаки строятся только по `event_date <= T`,
  таргет — сумма `gmv` в `(T, T+30]`;
- **панель валидации всегда 3-блочная** — это правило отбора, которым организатор
  собрал тестовые 250k («активен в каждом из трёх последних 30-дневных блоков»);
- **чистый коридор cutoff'ов 2025-04-03 .. 2025-10-16**: всё, что позже, отравлено
  (target-окно пересекает гарантированное окно активности панели);
- 4 фолда S1: `V ∈ {2025-09-04, 2025-09-18, 2025-10-02, 2025-10-16}`;
- рядом с RMSLE всегда смотреть `bias = mean log1p(y) − mean z`.

## Решение (текущее лучшее, LB public = 1.6507774106)

`S1-DIST-MIX` — смесь четырёх градиентных бустингов на одном наборе табличных
признаков, усреднённая в лог-пространстве и посаженная на измеренный уровень.
Карточка: `experiments/exp_014_s1_dist_head.md`.

**1. Панель и таргет.** На каждом cutoff'е `T` строка = пользователь из панели,
таргет = сумма `gmv` в окне `(T, T+30]`. Панель валидации и теста отбирается
правилом организатора (активен в каждом из 3 последних 30-дневных блоков),
панель обучения — 1-блочная: это надмножество, оно даёт на 14% больше данных,
а переприменение 3-блочного правила на обучении проверено и ухудшает CV.

**2. Признаки** (`src/features.py`, 227–236 колонок). Оконные агрегаты за
7/14/30/60/90/180/365 дней: присутствие, поиски, корзины, заказы, gmv, а также
доли, конверсии, средний чек, тренды между окнами и структура интервалов
(`gap_*`, `buygap_*`) и свежесть, нормированная на личный ритм. Пропущенные дни
**не** достраиваются нулями — «нет строки» и «строка из нулей» различаются.
Ключевая деталь: признаки с 365-дневным окном приводятся к сопоставимой годовой
ставке делением на реально доступную глубину истории (`--norm-long`), иначе они
означают разное на разных cutoff'ах — на раннем cutoff'е доступно 92 дня,
на тесте 409.

**3. Обучающая выборка.** Плотная сетка cutoff'ов шагом 7 дней по чистому коридору
`2025-04-03 .. 2025-10-16` — 29 cutoff'ов, ~6.07 млн строк. Всё, что позже
`2025-10-16`, отравлено: target-окно там попадает внутрь гарантированного окна
активности панели. Переход с 3 cutoff'ов на плотную сетку — крупнейший одиночный
выигрыш всей Strategy 1 (−0.0070).

**4. Модели и выходы.** Метрика — MSE в `z = log1p(y)`, поэтому L2 на `log1p(y)`
оптимизирует её точно. Четвёртый член смеси устроен иначе: **голова распределения**
(`dist`) предсказывает softmax по 16 бинам `z` (бин 0 = ровно ноль, остальные —
квантили `z|z>0`) и берёт `ẑ = Σ p_k·m_k` с центроидами, посчитанными на train.
Это оценка того же `E[z|x]`, но устойчивее к точечной массе в нуле и тяжёлому хвосту.

| вес | член | что отличает |
|---|---|---|
| 0.45 | `S1-DIST` | голова распределения, признаки `norm_long` |
| 0.30 | `S1-UNC` | L2, 236 ненормированных признаков |
| 0.15 | `S1-NORM` | L2, признаки `norm_long` |
| 0.10 | `S1-CAP` | L2, история усечена до 180 дней — страховка от сдвига train→test |

**5. Постпроцессинг.** Усреднение строго **в лог-пространстве** (в сыром GMV
неравенство Йенсена сместило бы уровень вверх), затем глобальный сдвиг
`δ = 2.3293 − mean(z)` и `pred = expm1(z + δ)`. Уровень `E[log1p(y)] = 2.3293`
не подобран, а **измерен** тремя сабмитами при разных δ: `MSE(L) = C + (L*−L)²`
восстанавливает `L*` до 7-го знака.

**Воспроизведение** — блок «Конфиг прогона» в `experiments/exp_014_s1_dist_head.md`.

```
│   ├── tune.py          — кривая по раундам, сетка гиперпараметров
│   ├── adversarial.py   — adversarial AUC против тестового cutoff'а
│   ├── error_analysis.py— сегментный разбор ошибок между двумя OOF
│   ├── smoke.py         — проверки корректности пайплайна

├── data/                — данные (не коммитим)

```

## Быстрый старт

```bash
pip install -r requirements.txt
# положить train.parquet и sample_submit.csv в data/raw/

python -m src.smoke                      # проверки: панель 250k, якорь 2.2421, лукап
python -m src.test_dist                  # проверки головы распределения
python -m src.test_pipeline              # проверки сборки матрицы и склейки OOF
python -m src.features --L 180 --min-history 90   # прогреть кэш фичей (~3 c/cutoff)
python -m src.train --exp MY-EXP --L 180 --min-history 90 --train-blocks 1 --cutoffs all
python -m src.predict --exp S1-BEST ...  # сабмит
```

Длинные прогоны запускать с `PYTHONIOENCODING=utf-8` — консоль Windows cp1251
роняет процесс на печати символов вне неё (`research/compute_profile.md`).

Дорогой эксперимент выгоднее гнать **разными процессами по фолдам** (LightGBM
плохо масштабируется по потокам, замеры в `research/compute_profile.md`):

```bash
LGB_THREADS=6 python -m src.train --exp E-A --val 2025-10-16 2025-09-04 --no-log ...
LGB_THREADS=6 python -m src.train --exp E-B --val 2025-10-02 2025-09-18 --no-log ...
python -m src.merge_oof --out E --parts E-A E-B --ref S1-E10 --desc "..."
```

Точные команды воспроизведения `S1-BEST` — в `research/strategy_1_results.md`.

## Ветки

- `main` — только через PR.
- `team-a`, `team-b` — рабочие ветки команд; Strategy 1 — `team-a-strategy-1-impl`.

Правила:
- Раз в день подливаем `main` к себе в ветку.
- Фичи только **добавляются новыми колонками**, чужие не переписываем.

## Принципы

1. Единая валидация на всех — только `src/validation.py`.
2. Один пайплайн фичей `build_features(T, L)` для train/val/test.
3. Только out-of-time валидация; коридор чистых cutoff'ов соблюдать строго.
4. Один эксперимент = одно изменение = одна строка в `experiments/log.csv`.
5. Результат любого эксперимента записывается, даже провал.
6. Параметры постпроцессинга подбираются только на OOF, никогда на leaderboard.
