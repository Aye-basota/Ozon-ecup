## 0. TL;DR — восемь фактов, которые определяют решение

| # | Факт | Почему это важно | Источник |
|---|------|------------------|----------|
| 1 | `sample_submit.predict` **точно равен** сумме `gmv` за 2026-01-15..2026-02-13 (100.00% совпадений) | Организаторский baseline = «персистентность». Даёт точный якорь уровня теста и калибровку CV↔LB | `e03` |
| 2 | Панель 250k отобрана правилом **«активен в каждом из трёх последних 30-дневных блоков»** (100.000% в блоках 0,1,2; 93.26% в блоке 3) | Историческая валидация без переприменения этого правила меряет **другую популяцию** (уровень таргета отличается на 0.198) | `e07`,`e08` |
| 3 | Любой cutoff `T ≥ 2025-10-17` **отравлен**: его target-окно пересекает гарантированное окно активности | Самый естественный cutoff `2026-01-14` даёт `P(активность)=1.0` — фатально оптимистичный CV | `e06`,`e07`,`e08` |

| 6 | Модель без усечения даёт на тесте уровень **2.6465** при якорном коридоре **2.28–2.41** | Перепрогноз 0.23–0.32; подтверждён независимо экстраполяцией дрейфа (−0.0027/день × 120 дней) | `e12` |
| 7 | В YoY-аналоге тестового окна (2025-02-14..03-15) `dm = +0.1659` — **максимум среди всех 18 чистых cutoff'ов года** (медиана +0.0370) | Целевое окно — сезонный подъём, а не пост-новогодний спад | `e09b` |
| 8 | 14.85% строк — «присутствие без активности» (все нули). При контроле на активность и GMV они поднимают `m_y` с 1.496 до 2.242 | Сильный сигнал, который теряется при наивном заполнении пропусков нулями | `e02`,`e07` |

> порядка **+0.07…+0.10** RMSLE. Выигрыш от смены класса модели и ансамблирования

### 1.2 Схема

```

user_id     int64      250 000 уникальных, диапазон 2..918 481
```

### 1.3 Колоночная алгебра — 6 из 18 колонок избыточны (`e02`)

Проверено на всех 30.6 млн строк, **0 нарушений**:

```
gmv       ≡ gmv_search + gmv_cat
to_ord    ≡ search_to_ord + cat_to_ord
to_cart   ≡ search_to_cart + cat_to_cart
has_search_to_cart ≡ 1[search_to_cart > 0]
has_search_to_ord  ≡ 1[search_to_ord  > 0]
has_cat_to_cart    ≡ 1[cat_to_cart    > 0]
has_cat_to_ord     ≡ 1[cat_to_ord     > 0]
search             ≡ 1[searches > 0]
gmv_search > 0     ⇒ search_to_ord > 0     (0 нарушений)
gmv_cat    > 0     ⇒ cat_to_ord    > 0     (0 нарушений)
to_ord     > 0     ⇒ gmv           > 0     (0 нарушений)
```

**Вывод.** Информативны ровно 10 полей: `event_date`, `user_id`, `cat`, `searches`,
`search_to_cart`, `search_to_ord`, `cat_to_cart`, `cat_to_ord`, `gmv_search`, `gmv_cat`.
Все `has_*` и `search` — производные; включать их в модель бессмысленно, они лишь
разбавляют `feature_fraction` и замедляют обучение.

Единственное исключение: `cat` — **не** производная, счётчика для каталога нет
(в отличие от `searches` для поиска). Это единственный «бинарный» источник информации.

## 2. `sample_submit.csv` — расшифрован полностью

### 2.1 Наблюдение (`e03`)

Проверены **все** окна: 30-дневные с разным сдвигом, окна длины 7/14/28/30/31/60/90/180/365/409,
а также `gmv_search` и `gmv_cat` по отдельности.

```
gmv 30d [2026-01-15..2026-02-13]   exact=100.00%  RMSLE=0.0000  corr(log)=1.0000
gmv 30d [2026-01-14..2026-02-12]   exact= 89.40%  RMSLE=0.4334
gmv 31d ending 2026-02-13          exact= 94.18%  RMSLE=0.3008
gmv_search 30d                     exact= 92.34%  RMSLE=0.4420
```

**`sample_submit.predict` = Σ `gmv` по пользователю за 2026-01-15..2026-02-13.**
Совпадение точное (atol=1e-6) для всех 250 000 строк.

### 2.2 Что это даёт

1. **Это не утечка таргета**, а baseline-персистентность. Ложная тревога снята —
   пользоваться им как ответом нельзя.
2. **Точный якорь уровня теста.** Из него напрямую считаются характеристики
   признакового окна на реальном тестовом cutoff:

   ```
   m_x     = mean(log1p(x_30d))      = 2.2421
   P(x>0)                            = 0.5407
   mu_x    = mean(log1p(x) | x>0)    = 4.1470
   ```

3. **Калибровка CV↔LB.** Если организатор покажет LB-скор baseline-сабмита,
   мы получим точное отображение локального RMSLE в LB: локально персистентность
   на чистом фолде даёт 2.2716 (`e08`). Разница локального и LB значения —
   это и есть поправка на популяцию и сезон.
4. Подтверждает, что таргет считается по колонке `gmv` (не `gmv_search`),
   суммированием без клиппинга, и что все 250k пользователей присутствуют в train.

### 2.3 Метрическое следствие (важно)

Для RMSLE-оптимального прогноза выполняется тождество
`mean_i log1p(ŷ_i) = E[log1p(y)]` (закон полного матожидания, т.к. оптимум —
это `ẑ_i = E[log1p(y_i) | x_i]`).

Значит **среднее `log1p` наших предсказаний обязано равняться истинному уровню таргета**.
Это жёсткая проверяемая константа, а не эвристика. Оценки уровня — в §5.3.

## 3. Правило формирования панели — главная структурная находка

### 3.1 Наблюдение (`e04`, `e06`, `e07`)

```
min(last_activity)  = 2026-01-15   = END − 29
max(first_activity) = 2025-12-15   = END − 60
```

Оба выполняются для **250 000 / 250 000** пользователей. Дальше — разложение по
30-дневным блокам, отсчитанным назад от 2026-02-13:

| блок | окно | активных | % |
|------|------|----------|---|
| 0 | 2026-01-15..2026-02-13 | 250 000 | **100.000%** |
| 1 | 2025-12-16..2026-01-14 | 250 000 | **100.000%** |
| 2 | 2025-11-16..2025-12-15 | 250 000 | **100.000%** |
| 3 | 2025-10-17..2025-11-15 | 233 152 | 93.261% |
| 4 | 2025-09-17..2025-10-16 | 225 431 | 90.172% |
| 5 | 2025-08-18..2025-09-16 | 218 793 | 87.517% |

Контроль — 30-дневные окна **не выровненные** по этой сетке дают 97.9–99.0%,
а не 100%:

```
[2026-01-10..2026-02-08] (сдвиг  5) 99.003%
[2025-12-31..2026-01-29] (сдвиг 15) 97.954%
[2025-12-01..2025-12-30] (сдвиг 45) 98.622%
```

**Правило отбора: пользователь имеет ≥1 активный день в каждом из трёх последних
30-дневных блоков, отсчитанных от даты отсечения.** Условие «первая активность
≤ T−60» выполняется автоматически как следствие блока 2.

### 3.2 Следствие A — какие cutoff отравлены

Гарантированное окно активности — `[2025-11-16 .. 2026-02-13]`. Target-окно
cutoff'а `T` — это `(T, T+30]`. Пересечение появляется при `T + 30 ≥ 2025-11-16`, т.е.

> **Чистые cutoff'ы: `T ≤ 2025-10-16`. Всё, что позже, отравлено.**

Замеры доли пользователей с хотя бы одной активностью в `(T, T+30]` (`e06`):

| T | пересечение с гарантией | P(активность в след. 30 дн.) |
|---|------------------------|------------------------------|
| 2025-11-15 | 0 дней | 100.000% |
| 2025-12-15 | 0 дней | 100.000% |
| 2025-12-16 | 1 день | 99.688% |
| 2025-12-31 | 16 дней | 98.039% |
| **2026-01-14** | **30 дней** | **100.000%** |

`T = 2025-11-15` и `2025-12-15` дают 100% потому, что их target-окна — это ровно
блоки 2 и 1 сетки. `T = 2026-01-14` — это ровно блок 0.

### 3.3 Следствие B — ловушка, в которую попадёт большинство (`e08`)

Валидация на чистом фолде `T = 2025-09-16` (target 2025-09-17..10-16):

```
обучение на 5 чистых cutoff'ах  → RMSLE 1.77114   bias = −0.086
обучение только на 2026-01-14   → RMSLE 1.82485   bias = +0.366   (+0.054 к RMSLE)
```

И зеркально — валидация **на** отравленном cutoff'е:

```
обучение на чистых → валидация на 2026-01-14  → RMSLE 1.72888  (оптимистичнее чистой на 0.042)
```

То есть выбор «возьмём самый свежий cutoff, он ближе всего к тесту» одновременно:
* даёт CV, завышенный примерно на **0.04 RMSLE**;
* учит модель пост-новогоднему **спаду** (`dm = −0.281`), тогда как тестовое окно —
  сезонный **подъём** (`dm ≈ +0.176`).

### 3.4 Следствие C — переприменять правило обязательно (`e08`)

На одном и том же cutoff `T = 2025-09-16`:

| панель | n | P(y>0) | mean log1p(y) |
|--------|---|--------|---------------|
| 3-блочная (как в тесте) | 190 690 | 0.6106 | 2.6431 |
| 1-блочная (наивная «активен за 30 дней») | 218 793 | 0.5685 | 2.4450 |

Разница уровня таргета — **0.198** в лог-пространстве. Модель, обученная на
неправильной панели, систематически недопрогнозирует.

### 3.5 Гипотеза — остаточное survivorship-смещение

Историческая панель на `T` содержит только тех, кто *дополнительно* дожил до
гарантированного окна (ноя-2025..фев-2026). Пользователи, удовлетворявшие правилу
на `T`, но ушедшие навсегда до ноября 2025, в датасете отсутствуют.

Косвенное подтверждение: размер 3-блочной панели монотонно растёт с приближением
к концу истории — 172 496 (2025-04-15) → 190 690 (2025-09-16) → 197 379 (2025-10-16)
→ 233 152 (2026-01-14) → 250 000 (тест). Тестовая панель — единственная
несмещённая, и она же самая широкая.

Практическое следствие: модель, обученная на старых cutoff'ах, **перепрогнозирует**
(наблюдаемый bias −0.086 при обучении на апр–авг и валидации на сентябре).
Этот эффект частично **компенсирует** сезонный недопрогноз из §5 — их нельзя
корректировать независимо, только суммарно и эмпирически.

## 4. Сущности, дубликаты, ID, утечки

### 4.1 `user_id` не несёт информации (`e04`)

```
corr(user_id, first_activity_day)  pearson −0.0016  spearman +0.0001
corr(user_id, last_activity_day)   pearson −0.0007  spearman +0.0003
corr(user_id, n_rows)              pearson −0.0019  spearman −0.0000
corr(user_id, log1p(gmv_total))    pearson +0.0008  spearman −0.0002
```

Разбиение на 20 бакетов по `user_id`: доля никогда не покупавших 11.6–12.5%,
средний GMV 1068–1120 — различий нет.

Структура пространства ID: 250 000 значений в диапазоне 2..918 481,
плотность 0.2722; `P(gap = 1) = 0.2717 ≈ 0.2722`; распределение разрывов
геометрическое, max gap = 44.

**Вывод.** `user_id` — равномерная случайная подвыборка ~27% из популяции ~918k.
Ни порядка регистрации, ни группировки, ни источника данных он не кодирует.
Как признак бесполезен; time-based/ordinal трюки по ID здесь не работают.
Побочно: разбиение public/private (50k/200k), скорее всего, тоже случайное
по пользователям — групповой структуры для эксплуатации нет.

### 4.2 Дубликаты и группы

* Пара `(user_id, event_date)` уникальна — агрегат по дню, дубликатов строк нет.
* Явных сущностей кроме пользователя нет: ни товара, ни категории, ни сессии,
  ни географии. Графовых/соседских связей между пользователями построить не из чего
  (нет общих объектов).
* Порядок строк в parquet — `user_id`, затем `event_date`; никакой скрытой
  информации в нём нет (row-groups по 122 880 строк, ровная нарезка).

### 4.3 Leakage audit

| канал | статус | комментарий |
|-------|--------|-------------|
| Target leakage в признаках | **нет**, если фичи строятся строго по `event_date ≤ T` | единственный источник таргета — `gmv`, он же признак; дисциплина cutoff обязательна |
| Утечка через `sample_submit` | **нет** — это персистентность, не таргет | но это законный источник якоря уровня (§2.2) |
| **Selection leakage через правило панели** | **есть, крупная** | §3.2–3.3. Это главный риск валидации |
| Temporal leakage | риск в trend-признаках | любые «будущие» окна запрещены; `build_features(cutoff)` обязателен |
| ID leakage | **нет** | §4.1 |
| Дубликаты train/test | неприменимо | train и test — одни и те же пользователи в разные периоды |
| Отложенная атрибуция | **есть, но мала** | 0.542% GMV приходится на дни без поисковой/каталожной сессии (`e04`) |

## 5. Время, сезонность и уровень таргета

### 5.1 Секулярный рост (`e05`)

Скользящий 30-дневный GMV по платформе:

```
2025-01-01..01-30  14.14M
2025-05-01..05-30  17.18M
2025-09-28..10-27  23.00M
2025-11-27..12-26  27.73M   ← новогодний пик
2025-12-27..01-25  21.99M   ← пост-праздничный спад
2026-01-15..02-13  21.01M   ← признаковое окно теста
```

Число покупателей в месяц: 91 313 (янв-25) → 146 182 (дек-25) → 135 459 (янв-26).
Рост примерно +50% год к году, обусловлен как ростом платформы, так и
онбордингом новых пользователей (первая активность у 189 446 из 250 000
приходится на январь 2025, далее 2.5–4.7k/мес до 2025-12-15).

### 5.2 Сезонность в лог-пространстве — то, что реально важно для RMSLE (`e09b`)

Замер сделан на **фиксированном определении панели** (1-блочное правило,
единственное конструируемое начиная с 2025-02-13), чтобы состав пользователей
не смешивался с сезонным эффектом.

`dm = mean log1p(y_{next30}) − mean log1p(x_{last30})`, разложенное на
экстенсивную (`dP` — доля покупающих) и интенсивную (`dmu` — средний лог-чек) части:

| cutoff | n | dm | dP | dmu | комментарий |
|--------|---|-----|-----|-----|-------------|
| **2025-02-13** | 190 797 | **+0.1659** | **+0.0298** | **+0.0804** | **YoY-аналог тестового cutoff — максимум года** |
| 2025-03-13 | 195 466 | −0.0791 | −0.0161 | −0.0211 | минимум года |
| 2025-05-08 | 201 274 | +0.0045 | −0.0010 | +0.0174 | |
| 2025-07-31 | 209 914 | +0.1143 | +0.0189 | +0.0596 | |
| 2025-09-11 | 217 820 | −0.0408 | −0.0064 | −0.0231 | |
| 2025-10-09 | 223 667 | +0.0326 | +0.0093 | −0.0125 | последний чистый |
| 2025-11-20 | 235 304 | +0.1224 | +0.0184 | +0.0752 | отравлен |
| 2025-12-04 | 242 273 | +0.1213 | +0.0163 | +0.0885 | отравлен |

Сводка по **18 чистым** cutoff'ам (`T ≤ 2025-10-16`):

```
dm      mean +0.0286   median +0.0370   std 0.0645   min −0.0791   max +0.1659
dP      median +0.0073
dmu     median +0.0197
```

**Ключевое.** `dm` YoY-аналога = **+0.1659** — это **максимум среди всех 18 чистых
cutoff'ов года**. Превышение над медианой: **+0.1290** в лог-пространстве.
Экстенсивная и интенсивная части обе примерно **вчетверо** выше типичных
(`dP` +0.0298 против медианы +0.0073; `dmu` +0.0804 против +0.0197).

В сыром масштабе отношение суммарного GMV target/hist за 2025 год = **1.1628**.

Причина — дневной календарный профиль (`e09b`). Все 30 дней целевого окна 2025 года
имели фактор > 1.0 относительно среднего дня признакового окна:

```
2025-02-14 Fri 1.100   2025-02-19 Wed 1.191   2025-02-28 Fri 1.190
2025-02-16 Sun 1.202   2025-02-23 Sun 1.076   2025-03-01 Sat 1.270
2025-02-17 Mon 1.096   2025-02-24 Mon 1.022   2025-03-03 Mon 1.367  ← пик
2025-02-18 Tue 1.091   2025-02-26 Wed 1.158   2025-03-06 Thu 1.277
                                              2025-03-08 Sat 1.065

```

Пик 1–6 марта (1.25–1.37) — предпраздничный спрос перед 8 марта; вторичный подъём
14–22 февраля — перед 23 февраля. Это **не** однодневные спайки, а устойчивый
месячный подъём, целиком попадающий в 30-дневный таргет.

**Оговорка (важно).** Наблюдение основано на **одном** годе. Структурная причина
(календарные праздники) даёт основания ожидать повторения, но это гипотеза, а не
доказанный факт. Величину поправки следует ограничивать (см. §5.3 и `strategy_1.md`).

Перекрёстная проверка через экстенсив/интенсив:
`P(y>0) ≈ 0.5407 + 0.0298 = 0.5705`, `mu_y ≈ 4.1470 + 0.0804 = 4.2274`,

> эмпирически на чистом фолде, а не применять как готовый множитель.

### 5.4 Наивный множитель ×1.16 не работает (`e05`)

```
персистентность            RMSLE 2.0333   (T = 2025-02-13)
персистентность × 1.1628   RMSLE 2.0594   (хуже!)
```

Потому что RMSLE доминируют пользователи с `y = 0` (46–60%), и умножение

по сырому GMV.

состав дней недели почти постоянен, поэтому как глобальный фактор бесполезен;

## 7. Что реально предсказывает таргет

### 7.1 Наивные предикторы на чистом фолде `T = 2025-09-16` (`e08`)

```
персистентность: gmv за 30 дней           RMSLE 2.27156
gmv за 90 дней / 3                        RMSLE 2.11006
gmv за 180 дней / 6                       RMSLE 2.06978
gmv за 365 дней / 12.17                   RMSLE 1.95780   ← лучший наивный
лучшая константа (log-space 2.640)        RMSLE 2.35508
```

Монотонное улучшение с ростом окна усреднения — на **0.31 RMSLE** от 30 к 365 дням.
Сигнал в этой задаче почти целиком долгосрочный; недавний оборот — шумная
реализация устойчивой «ценности» пользователя. RMSLE вознаграждает усадку
(shrinkage) к условному среднему, а не воспроизведение последнего значения.

### 7.2 Важность признаков модели (`e08`, top-10 по gain)

```
w180_days_buy         6 587 225     ← число дней с покупкой за 180 дней
w180_orders           3 681 544
w90_days_buy          1 699 229
w90_orders            1 117 986
rec_over_buygap         695 995     ← recency, нормированная на личный интервал покупок
w365_days_buy           375 333
lifetime_gmv_per_day    352 249
w365_orders             302 659
w180_lgmv_std           209 359
all_days_buy            190 531
```

Доминирует **частота покупок на длинном окне**, а не денежные суммы и не
свежие 7/30-дневные агрегаты. Это прямо указывает на BTYD-структуру задачи
(frequency × recency × monetary), где frequency несёт основную массу сигнала.

Признак `rec_over_buygap = rec_buy / buygap_mean` (свежесть последней покупки,
делённая на средний личный интервал между покупками) — 5-й по важности,
хотя это простое отношение двух других признаков. Персонализованная нормировка
recency работает.

### 7.3 Анатомия ошибки (`e12`, фолд `T = 2025-09-16`, RMSLE 1.77086)

По истинному исходу:

| сегмент | n | доля | RMSLE | доля MSE |
|---------|---|------|-------|----------|
| `y = 0` | 74 249 | 38.9% | 1.9586 | **47.6%** |
| `y > 0` | 116 441 | 61.1% | 1.6399 | 52.4% |

По исторической частоте покупок:

| `w180_days_buy` | n | доля | RMSLE | доля MSE | P(y>0) | оптим. offset |
|-----------------|---|------|-------|----------|--------|---------------|
| 0 | 25 220 | 13.2% | 1.3216 | 7.4% | 0.148 | −0.070 |
| 1 | 16 651 | 8.7% | 1.7608 | 8.6% | 0.306 | −0.100 |
| 2–3 | 27 665 | 14.5% | 1.9415 | **17.4%** | 0.432 | −0.135 |
| 4–7 | 39 212 | 20.6% | 2.0464 | **27.5%** | 0.611 | −0.115 |
| 8–15 | 42 074 | 22.1% | 1.9203 | **25.9%** | 0.803 | −0.090 |
| 16+ | 39 868 | 20.9% | 1.4047 | 13.2% | 0.951 | −0.050 |
| никогда не покупал | 20 600 | 10.8% | 1.2292 | 5.2% | — | — |

**Вывод.** 70.8% всей MSE сосредоточено в трёх средних сегментах (2–15 дней с покупкой

посегментная калибровка потенциально полезна.

### 7.4 Out-of-time дрейф и артефакт глубины истории (`e12`)

#### Дрейф растёт линейно с разрывом train→val

Обучение на cutoff'ах июнь/июль/август 2025:

| фолд | разрыв | RMSLE | mean bias | оптим. offset | RMSLE после | выигрыш |
|------|--------|-------|-----------|---------------|-------------|---------|
| 2025-09-16 | 32 дн | 1.77086 | **−0.0913** | −0.0900 | 1.76851 | +0.0024 |
| 2025-10-16 | 62 дн | 1.75921 | **−0.1671** | −0.1650 | 1.75126 | +0.0080 |

Смещение отрицательное — модель **перепрогнозирует**, и почти точно линейно
по разрыву: −0.00285 и −0.00270 на день. Экстраполяция на реальный разрыв
(последний чистый cutoff 2025-10-16 → тест 2026-02-13 = **120 дней**) даёт
ожидаемое смещение около **−0.32**.

#### Независимое подтверждение через якорь уровня

Та же модель, применённая к тестовому cutoff'у:

```
mean(log1p(pred)) на тесте          = 2.6465
якорный коридор (§5.3)              = 2.28 .. 2.41
перепрогноз                          = +0.24 .. +0.37
```

Два независимых метода — экстраполяция дрейфа и якорь из `sample_submit` — сходятся
на перепрогнозе **~0.25–0.35** в лог-пространстве. Это самая крупная одиночная
поправка, обнаруженная в исследовании.

Порядок величины выигрыша: при `RMSLE = sqrt(σ² + b²)` и `σ ≈ 1.80`, `b = 0.30`
исправление смещения даёт **≈ 0.025 RMSLE**. Локально на фолдах этот выигрыш
выглядит крошечным (+0.0024 / +0.0080), потому что там `b` вчетверо меньше,
а зависимость квадратичная. **Локальный CV принципиально недооценивает важность
этой поправки.**

#### Причина: adversarial validation

| пара | AUC |
|------|-----|
| 2025-09-16 vs TEST | **0.9930** |
| 2025-10-16 vs TEST | **0.9912** |
| 2025-09-16 vs 2025-10-16 (два исторических) | 0.9811 |

Драйверы разделения (по gain, обе пары): `tenure`, `first_buy_age`,
`all_days_present`, `gap_mean`, `gap_max`, `gap_std`, `trend_pres_90_365`,
`w365_days_present`.

Это **все признаки с неограниченным или очень длинным окном**. Причина механическая:
доступная глубина истории на cutoff'е `T` равна `T − 2025-01-01`, то есть

```
2025-03-31 (начало коридора)   89 дней
2025-10-16 (конец коридора)   288 дней
2026-02-13 (тест)             409 дней
```

`tenure`, `all_*`, `w365_*` на разных cutoff'ах измеряют **разные вещи**.
Дерево, обученное при `tenure ≤ 288`, на тесте получает значения до 409 и
отправляет всех в одну ветку — это отказ экстраполяции, а не сдвиг данных.

Сдвиг средних подтверждает:

| признак | val 2025-10-16 | TEST | отношение |
|---------|----------------|------|-----------|
| `tenure` | 268.78 | 366.60 | **1.364** |
| `rec_buy` | 33.43 | 43.80 | 1.310 |
| `w365_gmv` | 875.49 | 1004.53 | 1.147 |
| `w30_gmv` | 111.49 | 84.03 | **0.754** |
| `w30_orders` | 3.30 | 2.80 | 0.848 |
| `trend_gmv_30_90` | 0.831 | 0.680 | 0.818 |

Здесь смешаны два разных эффекта:

* **артефакт** — `tenure`, `all_*`, `w365_*` растут просто потому, что у теста больше
  доступной истории;
* **реальный сдвиг** — `w30_gmv` ниже на 25%, `w30_orders` на 15%: признаковое окно
  теста (2026-01-15..02-13) попадает в пост-новогодний провал.

Модель видит высокие длинные агрегаты (в 365-дневное окно теста попадает декабрьский пик)
и прогнозирует высоко, хотя недавняя активность подавлена. Отсюда перепрогноз.

> **Практическое следствие.** Рекомендация из `DISCRIPTION.md` включить окно
> «весь доступный период» — это ровно тот признак, который создаёт артефакт.
> Требуется либо ограничить окна фиксированной глубиной `L`, одинаковой на всех
> cutoff'ах включая тест, либо явно убрать неограниченные признаки.
> Замер эффекта такой правки — `research/eda/e13_capped.py`.

## 8. Метрика: что именно оптимизируем

`RMSLE = sqrt( mean_i ( log1p(y_i) − log1p(max(0, ŷ_i)) )² )`

1. Это **обычный MSE в переменной `z = log1p(y)`**. Оптимальный прогноз —
   `ẑ_i = E[z_i | x_i]`, а сабмит — `ŷ_i = expm1(ẑ_i)`.
   Обучение GBM с L2-лоссом на `log1p(y)` **уже оптимизирует метрику точно** —
   никакого custom objective не требуется. Это важно: экзотические лоссы здесь
   не источник преимущества.
2. **Все пользователи равнозначны** (простое среднее по 250k). Крупные клиенты
   не важнее мелких — прямое следствие лог-шкалы.
3. **Устойчивость к выбросам**: ошибка в 10× по GMV даёт вклад `(ln 10)² ≈ 5.3`
   независимо от абсолютного размера. Поэтому «поймать кита» ничего не даёт,
   а завысить прогноз спящему пользователю — дорого.
4. **Калибровка важнее ранжирования.** Метрика не ранговая; сдвиг всех прогнозов
   на константу `δ` в лог-пространстве меняет скор как
   `sqrt(σ² + δ²)`. Отсюда — обязательная проверка `mean(log1p(pred))` (§2.3).
5. **Разложение**: `E[z] = P(y>0) · E[z | y>0]`, т.к. `z = 0` при `y = 0`.
   Двухчастная модель (классификатор × условная регрессия) и прямая регрессия
   на `log1p` целятся в одну и ту же величину. Замер (`e08`):
   прямая 1.77114, двухчастная 1.77008, блендинг 50/50 **1.76823**.
   Выигрыш есть, но небольшой (−0.003) — это источник **разнообразия для ансамбля**,
   а не самостоятельное преимущество.
6. **Клиппинг `max(0, ŷ)`** обязателен по правилам, но при работе через
   `expm1(ẑ)` отрицательных значений не возникает по построению.
7. **Квантильное сопоставление / distribution matching противопоказано.**
   Оптимум — условное среднее, оно по построению «уже» истинного распределения.
   Растягивание прогнозов до формы распределения таргета гарантированно ухудшит RMSLE.

## 9. Выводы по валидации

1. **Только out-of-time**, cutoff-схема, как и требует `DISCRIPTION.md` и `src/validation.py`.
2. **На каждом cutoff `T` переприменять 3-блочное правило панели.**
   Без этого популяция не совпадает с тестовой (§3.4).
3. **Жёсткая граница: `T ≤ 2025-10-16`.** Более поздние cutoff'ы отравлены
   гарантией активности. `2026-01-14` использовать нельзя ни для обучения,
   ни для валидации.
4. **Нижняя граница: `T ≥ 2025-03-31`** — раньше не хватает 90 дней истории
   для построения панели.
   Итого рабочий коридор cutoff'ов: **2025-03-31 .. 2025-10-16**, около 200 дней.
5. **Отдельный сезонный фолд `T = 2025-02-13`** (target 2025-02-14..2025-03-15) —
   единственный календарный аналог теста. Полное 3-блочное правило на нём
   построить нельзя (нет данных до 2025-01-01), 1-блочное — можно.
   Использовать как **калибровочный**, а не как основной фолд.
6. **Несколько сценариев валидации одновременно** (см. `strategy_comparison.md`),
   потому что две систематические силы — сезонный подъём (+) и survivorship (−) —
   действуют навстречу друг другу, и ни одна не измеряется чисто.
7. **Риск LB-переобучения.** Public = 50k пользователей (20%). Стандартная ошибка
   RMSLE при n=50 000 порядка `σ_e² / sqrt(2n) / RMSLE` ≈ 0.005–0.007.
   Разницу меньше ~0.01 на public LB считать шумом и не принимать по ней решений.

## 10. Модельные пробы: что даёт выбор класса модели (`e14`, `e15`)

Все замеры — фолд `T = 2025-09-16`, 3-блочная панель, обучение на cutoff'ах
июнь/июль/август 2025, LightGBM 600 раундов. База — **1.77086**.

| постановка | RMSLE | комментарий |
|------------|-------|-------------|
| 227 ручных агрегатов (база) | **1.77086** | |
